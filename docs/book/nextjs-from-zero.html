Terminal ve Git

Klasörden depoya, depodan GitHub'a. Kod yazmadan önceki her şey.

Neden terminal

Kullanacağın araçların çoğunun düğmesi yok — git'in yok, npm'in yok, veritabanı bağlantısının yok. Bu bir eksiklik değil, tercih.

Sebebi şu: tıklamayı kimseye gönderemezsin. "Şuraya tıkla, sonra oraya" diye anlatmak zorunda kalırsın. Ama git init -b main satırını kopyalayıp yapıştırabilirsin — ve altı ay sonra kendine de yapıştırabilirsin.

terminal Bilgisayara yazıyla komut verdiğin pencere. Komut satırı veya konsol da deniyor.

Tarayıcıda F12 → Console'a document.title yazarsın, cevap verir. Terminal aynı şey — ama tek bir sayfayla değil, bütün bilgisayarla konuşuyorsun.

Çalışma klasörü

Terminal her an bir klasörün içinde duruyor. Yazdığın komutlar oraya uygulanıyor. Bir odada durmak gibi: "ışığı aç" dediğinde bulunduğun odanın ışığı açılır. 

pwd/Users/adin/Desktop/rung

pwd = print working directory

Sürüm kontrolü

Herkesin ilk çözümü aynıdır:

style.css
style-yedek.css
style-son.css
style-son-GERCEK.css

Bu çalışmıyor. Üç şeyi bilmiyorsun: hangisi neydi, neyi neden değiştirdin, ve iki dosyada birden çalıştıysan hangi ikisinin uyumlu olduğunu.

Sürüm kontrolü, projenin zaman içindeki her hâlini notuyla birlikte saklayan sistem. En yaygını Git. Oyunlardaki kayıt noktası gibi — ama kayıtların hepsi duruyor, her birinin notu var, ve aralarındaki farkı satır satır görebiliyorsun. 

git init -b mainInitialized empty Git repository in .../rung/.git/
initinitialize — bu klasörü depoya çevir
-b mainbranch — ana dalın adı main olsun
neden -b main Yazmazsan Git dalı master diye adlandırır ve bir uyarı basar. main bugün standart; sonradan değiştirmek fazladan iş. Baştan doğrusunu yaz.

Git'in üç bölgesi

Git'te "kaydet" tek komut değil, iki. Sebebi şu: bir öğleden sonra iki iş yapmış olabilirsin — bir hata düzelttin ve renkleri değiştirdin. Tek komut olsaydı ikisi aynı kayda girerdi, birini geri alırken diğeri de giderdi.

tuzak · burada takıldık git add bir işaret koymuyor. Dosyanın o andaki içeriğinin kopyasını alıyor.

Sonuç: git add yaptıktan sonra dosyayı tekrar düzenlersen, o düzeltme commit'e girmez. Tepsideki fotoğrafta hâlâ eski hâli var. Tekrar git add gerekiyor.

Böyle bir durumda git status aynı dosyayı iki bölümde birden gösterir.

Ne kaydedilmez

.DS_Store dosyasını sen oluşturmadın — macOS Finder her klasörü açtığında bırakıyor. Depoya koyarsan iki sorun: her açışta değiştiği için gerçek değişikliklerin arasında gürültü yapar, ve ikinci bir kişi katılırsa kimsenin umursamadığı bir dosya için çakışma çıkar.

kural Depo, projenin ne olduğunu tutar — senin bilgisayarının arkasında bıraktığı izleri değil. Genellemesi: üretilen şey depoya girmez, üreten şey girer.

en pahalı tuzak .gitignore sadece takip edilmeyen dosyalara uygulanır. Bir dosya bir kez takibe girdiyse, sonradan eklemek onu durdurmaz — git rm -r --cached gerekir.

Ve geçmiş yine dolu kalır: her git clone o veriyi indirmeye devam eder. Gerçekten silmek geçmişi yeniden yazmayı gerektirir, bütün commit kimlikleri değişir.

.gitignore koruma, tedavi değil. Bu yüzden .env satırı, o dosya daha doğmadan önce yazılır. Bir anahtar bir kez commit edilirse yanmıştır.

Commit mesajı

Commit atmak kolay, zor olan mesajı yazmak. Altı ay sonra update, fix, son hali, asdasd gibi bir liste sana hiçbir şey söylemez. Ve bir işverenin repona bakınca gördüğü ilk şey bu liste.

Conventional Commits bir yazım standardı. Kural tek satır: tip: ne yaptığın

featYeni bir özellik eklendi
fixBir hata düzeltildi
docsSadece belge değişti
refactorDavranış aynı, kod yeniden düzenlendi
testTest eklendi veya değişti
choreYapılandırma, araç, kurulum
kural Mesaj İngilizce, küçük harfle başlar, emir kipiyle yazılır. "added" değil add. Sebebi: commit, "bu commit uygulandığında ne olur" sorusunun cevabıdır.

Ve bir commit bir iş yapar. İki iş varsa hedefli git add dosya-adı ile ikiye böl — sonra birini geri almak isteyince diğeri yerinde kalır.

tuzak -m yazmazsan git bir metin editörü açar — muhtemelen vim, ve çıkmayı bilmezsen orada sıkışırsın. Kurtuluş: :q! + Enter.

Uzak depo

Bütün geçmişin tek bir diskte duruyor. İki sıkıntı: disk ölürse aylar uçar, ve kimse göremez — kimsenin göremediği portfolyo, portfolyo değil.

git ≠ github Git bilgisayarında çalışan program, internet gerektirmez. GitHub git depolarını barındıran bir şirket — git'in parçası değil, sadece en popüler ev sahibi.
-u bayrağı git push -u origin main — -u = --set-upstream: "yereldeki main, origin'deki main'i takip etsin."

Dal başına bir kez. Sonra git push yeter. Ama yeni bir dal açarsan onun için tekrar gerekir.

gerçekten başımıza geldi

"Deploy ettim ama site değişmedi"

Kod yazıldı, commit atıldı, Vercel'de deploy tetiklendi — ama canlıda eski sayfa duruyordu. Yarım saat kaybettik.

Cevap git status'un ilk satırındaydı:

## main...origin/main [ahead 2]

ahead 2 = "yerelde iki commit var, GitHub'da yok." Vercel GitHub'dan yayınlıyor, senin diskinden değil.

Ders: git commit ≠ yayın. git push = yayın. Ve git status'un ilk satırı bunu her zaman söylüyor.

Node, npm ve paketler

JavaScript'i tarayıcının dışına çıkarmak — ve neden mecburuz.

Neden sunucu gerekiyor

Bir web uygulamasının üç işi tarayıcıda yapılamaz:

  • Veritabanına bağlanmak — şifre gerekiyor
  • Bir API'ye anahtarla istek atmak — anahtar gerekiyor
  • Başka kullanıcıların verisini gizlemek — "gizle" diyen kodun kullanıcıda olmaması gerekiyor

Ortak nokta: hepsinde kullanıcının görmemesi gereken bir şey var.

tuzak Tarayıcıya gönderdiğin her satır kodu kullanıcı okuyabilir — F12 yeter. Bir API anahtarını oraya koyarsan biri kopyalar, senin hesabından binlerce istek atar, fatura sana gelir.

Kodu karıştırıp gizlemek işe yaramaz: tarayıcı o anahtarı kullanabiliyorsa, bir insan da onu çıkarabilir. Tek çözüm anahtarın tarayıcıya hiç gitmemesi.

npm ve paketler

Paket = başkasının yazıp paylaştığı, kurup kullanabileceğin kod parçası. npm install <paket> yazınca npm onu internetten indirip node_modules/ klasörüne koyuyor ve package.json'a bir satır yazıyor.

Kurmak = başkasının kodunu projenin içine indirmek. Sihir yok.

react çalışıyor → dependencies. typescript sadece kontrol ediyor, derleme bitince yerde kalıyor → devDependencies (npm install -D).

03

TypeScript

Çalışmayan, sadece bakan bir katman. Ve tam da bu yüzden değerli.

Sessiz yanlış

const density = entry.errors / entry.wordCount * 100;

entry.wordCount bir sayı mı? Veritabanından string olarak gelmiş olabilir. Öyleyse "74" / 4 → 18.5. Çalışır, hata fırlatmaz, ve yanlıştır.

Çöken kodu düzeltirsin. Sessizce yanlış olan sayıyı aylarca fark etmezsin.

Ne olduğu, ne olmadığı

TypeScript, JavaScript'in üzerine tip ekleyen katman. Yeni bir dil değil — her geçerli JavaScript, geçerli TypeScript.

en önemli cümle TypeScript çalışmaz. Sunucuya ve tarayıcıya giden şey derlenmiş JavaScript; tip işaretleri derlemede siliniyor. Tek satırı bile canlıya gitmiyor.

Ne zaman hangisi devreye giriyor: editörde sürekli kontrol · npm run dev tip hatasında durmaz, sadece uyarır · npm run build durur. Yani bozuk tiple canlıya çıkamıyorsun.

@types/… paketleri React düz JavaScript ile yazılmış, içinde tip bilgisi yok. @types/react onun kullanma kılavuzu — içinde çalışan tek satır kod yok, sadece tanım.

Bu yüzden react dependencies'te ama @types/react devDependencies'te: biri çalışıyor, diğeri sadece anlatıyor.

Katı mod

tsconfig.json'da "strict": true. Next.js varsayılan olarak false koyuyor — mevcut bir projeye eklendiğinde yüzlerce hata fırlatmasın diye. Yeni bir proje için doğru varsayılan değil.

İki şeyi yakalıyor:

  • Tipsiz parametre. function f(x) → "x implicitly has an 'any' type"
  • null kontrolü. el.textContent → "el is possibly null". JavaScript'te en sık çökme sebebi buydu; katı mod onu sen yazarken yakalıyor.
daraltma — narrowing process.env.X'in tipi her zaman string | undefined, çünkü TypeScript .env dosyasının içini bilmiyor. 
const url = process.env.DATABASE_URL;   // string | undefined
if (!url) throw new Error("...");        // boşsa burada duruyor
const sql = neon(url);                   // string

TypeScript kodun akışını takip ediyor: "boş olsaydı üstte durmuştu, demek ki dolu."

! koyup susturmak da mümkündü — yapma. Katı modu açıp susturmak anlamsız. Yan fayda: değişken eksikse anlamsız çökme yerine ".env.local'i kontrol et" yazan bir hata alıyorsun.

Klasik React'ta index.js'i sen yazar, ReactDOM.render()'ı sen çağırırdın. Next.js'te o kodu Next.js üretiyor ve .next/ klasörüne yazıyor.

.next/ = senin elle yazacağın bağlantı kodunun durduğu yer. Zaten bu yüzden .gitignore'da: üretilen şey depoya girmez.

Bir sayfada iki zıt ihtiyaç var: veritabanına erişmek (şifre gerekiyor, kullanıcıya gitmemeli) ve düğmeye tepki vermek (kullanıcının parmağı orada, kod onda olmalı).

Next.js varsayılanı sunucu yaptı. Tarayıcıda çalışması gerekeni sen işaretliyorsun: 

// dosyanın EN ÜSTÜ, her şeyden önce
"use client";
en çok yanlış anlaşılan yer "use client" bir düğme değil, bir SINIR.

İşaretlediğin dosya tek başına gitmiyor — o dosyanın import ettiği her şey de tarayıcıya iniyor. Ve onların import ettikleri de.

gerçekten başımıza geldi

password authentication failed

Ortam değişkeni panele girilmişti, ama derleme çöküyordu:

Error [NeonDbError]: password authentication failed
for user 'neondb_owner'

Hata çok şey söylüyordu: değişken vardı (yoksa bizim throw'umuz çalışırdı), adres doğruydu, kullanıcı adı tanınmıştı. Sadece şifre yanlıştı.

Sebep: .env.local'de değer tırnak içinde yazılıyor — DATABASE_URL="postgres://…". O tırnaklar dosya biçiminin parçası, Next.js onları soyuyor. Panelin form kutusu ise dosya değil: ne yapıştırdıysan harfi harfine alıyor.

Aynı metin, iki farklı kural. Dosyada tırnak gerekir, panelde gerekmez.

Statik mi, dinamik mi

Next.js varsayılan olarak sayfayı derlemede bir kez üretiyor. Çoğu sayfa için doğru: bir kez üret, dağıt, veritabanına hiç dokunma. Çok hızlı.

Ama kullanıcı verisi gösteren sayfada bu yanlış — veri donuyor.

StatikDinamik
Sorgu ne zamanDerlemede, bir kezHer istekte
Doğru olduğu yerTanıtım sayfası, belgeKullanıcı verisi
sinsi tuzak Statik sayfa çalışıyor gibi görünür — veri var, sayfa açılıyor. Ama gösterdiği şey derleme anından kalma.

Teşhis: sayfayı iki kez yenile. Değişmiyorsa statik. Ya da npm run build çıktısında ○ (Static) ara. Ya da yanıt başlığına bak: x-vercel-cache: HIT → statik, MISS → dinamik.

Çözüm: export const dynamic = "force-dynamic";

Bir yan etkisi daha var: statikken sorgu derlemede çalıştığı için ortam değişkeni build anında gerekiyor. Yoksa derleme çöküyor ve eski sürüm servis edilmeye devam ediyor.

Boş bir klasörden başladın. Şimdi internette bir adres var, açınca sayfa geliyor, ve sayfadaki sayı her istekte başka bir kıtadaki veritabanından geliyor.

Cevaplar

Cevaba bakmadan önce kendi cümleni kur. Yarısı doğruysa asıl öğrenilecek yer yanlış olan yarısı — kitabın çıktığı projede en çok orada ilerlendi.

Bölüm 01 — Terminal ve Git

01 · 1

git add index.html yazdın, sonra aynı dosyada bir satır daha değiştirdin ve git commit attın. Son değişiklik commit'e girdi mi?

Girmedi. add bir işaret koymuyor, dosyanın o andaki içeriğinin kopyasını alıyor. Sonraki düzenleme yeni bir içerik — tekrar git add gerekiyor. git status böyle bir durumda aynı dosyayı iki bölümde birden gösterir.

01 · 2

GitHub yarın kapansa projen gider mi?

Gitmez. Git dağıtık: .git klasöründe bütün geçmişin tam kopyası senin diskinde duruyor. GitHub sadece bu depoları barındıran popüler bir ev sahibi — Git'in parçası değil.

01 · 3

.env.local'i yanlışlıkla commit'ledin, fark edip .gitignore'a ekledin. Şifren güvende mi?

Değil. .gitignore sadece takip edilmeyen dosyaları gizler ve geçmişi temizlemez; şifre eski commit'in içinde duruyor. Tek doğru hamle: anahtarı iptal et, yenisini al.

Bölüm 02 — Node, npm ve paketler

02 · 1

node_modules/ klasörünü sildin, proje çalışmaz oldu. Bu klasör depoya girmiyorsa nasıl geri geliyor?

npm install ile. Liste package.json'da, hangi sürümün kurulduğu package-lock.json'da yazıyor. İkisi depoda olduğu için klasör her makinede birebir yeniden kurulabiliyor.

02 · 2

typescript neden devDependencies'te ama @neondatabase/serverless dependencies'te?

Ölçüt tek soru: canlıdaki sunucu buna çalışırken ihtiyaç duyuyor mu. TypeScript sadece derleme ve kontrol sırasında lazım, derleme bitince yerde kalıyor. Veritabanı sürücüsü ise her istekte çalışıyor.

02 · 3

Tarayıcıda document.title yazınca cevap alıyorsun, Node'da yazınca hata. Dil mi farklı?

Dil aynı, ortam farklı. document ve window tarayıcının verdiği araçlar. Node'da tarayıcı yok; onun yerine dosya okuma, ağ dinleme gibi tarayıcının vermediği araçlar var.

Bölüm 03 — TypeScript

03 · 1

npm run dev tip hatasında durmuyor, npm run build duruyor. Bu neden kasıtlı?

Yazarken her yarım satırda durmak işi keser — o yüzden geliştirme sunucusu sadece uyarır. Asıl tehlike bozuk tiple canlıya çıkmak, o yüzden kapı üretim derlemesinde.

03 · 2

process.env.DATABASE_URL'in tipini TypeScript neden string | undefined sayıyor?

Çünkü .env dosyasının içini bilmiyor; ortam değişkeni çalışma anında geliyor. if (!url) throw … yazdığında akışı takip edip altta artık dolu olduğunu anlıyor — buna daraltma (narrowing) deniyor.

03 · 3

Tip bilgisi canlıdaki koda hiç girmiyorsa TypeScript sana ne kazandırıyor?

Hatayı çalıştırmadan önce yakalamayı. entry.errors / entry.wordCount gibi bir satır çökmeden, sessizce yanlış sayı üretir; tip kontrolü onu sen yazarken söyler.

Bölüm 04 — Next.js'in iskeleti

04 · 1

page.tsx'i hiçbir yerden import etmiyorsun, yine de sayfa ekrana geliyor. Onu kim çağırıyor?

Next.js. Klasör ağacını okuyup çağıran kodu kendisi üretiyor ve .next/ klasörüne yazıyor. Klasik React'te o satırı sen yazıyordun; burada senin elinle yazacağın kod artık üretiliyor.

04 · 2

export default function Sayfa() — adını Sayfa koydun, çalıştı. Peki export const metadata yerine export const sayfaBilgisi yazsan?

Çalışmaz — hata da vermez, sessizce görmezden gelinir. Kural: export default dosyada tek olduğu için adına bakılmaz; isimli export'ta aranan adın kendisidir.

04 · 3

Aynı üst bar üç sayfada duruyor ve sekme değiştirince yanıp sönmüyor. Bunu hangi dosya sağlıyor?

layout.tsx. Kabuk yerinde kalıyor, sadece {children}'ın oturduğu yer yeniden çiziliyor. Üç dosyaya kopyalasaydın logo değişince üç yeri düzeltmen gerekirdi.

Bölüm 05 — Next.js — tam harita

05 · 1

app/kayit/[id]/page.tsx — 142 kayıt için kaç dosya yazacaksın?

Bir tane. Köşeli parantez o konumdaki her değeri kabul ediyor; hangi değerin geldiği sayfaya parametre olarak veriliyor. /kayit/42 ile /kayit/117 aynı dosyaya düşüyor.

05 · 2

Bir dosyanın en üstüne "use client" yazdın. O dosya db.ts'i import ediyor. Ne oldu?

db.ts de tarayıcıya indi — "use client" bir düğme değil, bir sınır; sınırın altındaki her şey iniyor. Şifren artık herkeste. Doğrusu: sınırı yaprağa yakın tut, sadece düğmenin kendisini işaretle.

05 · 3

Sayfa veritabanından saat gösteriyor ama saat hep aynı kalıyor. Teşhis?

Sayfa statik kalmış: sorgu derlemede bir kez çalışmış, sonuç metne gömülmüş. Kullanıcı verisi gösteren sayfa dinamik olmalı — export const dynamic = "force-dynamic".

Bölüm 06 — Sunucu tarafı ve veritabanı

06 · 1

Server Component'e koyduğun console.log nerede çıkar — ve bu neden bütün mimariyi özetler?

Terminalde, tarayıcı konsolunda değil. Çünkü fonksiyon sunucuda çalıştı; tarayıcıya sadece ürettiği HTML gitti. Kodun kendisi hiç inmedi.

06 · 2

Klasik React'te sayfanın kaynağında <div id="root"> boş görünürdü, şimdi içerik dolu. Kullanıcı için pratik farkı ne?

İlk açılışta boş ekran ya da dönen çember yok — içerik ilk karede orada. Arama motorları da metni doğrudan görüyor, JavaScript'in çalışmasını beklemiyor.

06 · 3

NEXT_PUBLIC_ ön ekini koymadıkça ortam değişkeni tarayıcıya gitmiyor. Bu ön ek neyi zorunlu kılıyor?

Bilinçli onayı. Sızdırmak için fazladan bir şey yazman gerekiyor; kazara olmuyor. Ön eki gördüğün an "bu değer herkese açık" diye okuyabiliyorsun.
